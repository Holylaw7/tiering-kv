# ADR-0003: Concurrency Model

## Status

Accepted

## Context

Redis 是单线程模型，吞吐依赖单核与事件循环；Tiering-KV 面向多核服务器与
1k–100k 并发连接，同时要求热点 GET P50 < 0.5ms，并支持异步冷热迁移与磁盘 IO。
需要确定线程模型与共享数据并发控制策略。

## Decision

1. **网络层：Netty 事件循环模型（NIO）**
   - Boss 线程接受连接，Worker 线程处理 IO；
   - IO 线程不执行阻塞操作，命令解码后投递到工作线程池；
   - 背压：工作队列有界，达到阈值时暂停读取（`autoRead=false`）并返回 -BUSY。
2. **命令执行：有界工作线程池 + 按 key 哈希分片**
   - 同一 key 的命令保持顺序执行，不同 key 并行；
   - 兼顾单 key 语义与多核扩展。
3. **内存表并发：分段锁（striped locks）替代全局锁**
   - 分片哈希表（初始 64 分片），每分片独立锁；
   - 只读热路径使用不可变快照/volatile 发布，写入经分片锁；
   - Phase 7 评估 LongAdder / Striped 及无锁结构（需新 ADR）。
4. **热度管理：采样式后台线程**
   - Hotness Manager 按时间窗口（如 100ms）从各分片采样访问计数；
   - LFU 衰减与 ARC 列表更新在专用调度线程完成，不阻塞请求路径。
5. **冷热迁移：异步调度**
   - `scheduler` 使用有界队列 + 专用迁移线程池；
   - 迁移任务可取消、可重试，失败不影响主读写路径。
6. **禁止全局锁**；跨分片操作（迁移、flush）通过分片间协调协议或分阶段锁完成。

## Alternatives

1. **thread-per-connection**：实现简单，但 100k 连接下线程数与上下文切换不可接受。
2. **纯事件循环（无工作线程）**：无法承载磁盘/迁移 IO 阻塞，命令处理必然卡住
   事件循环。
3. **Java 21 虚拟线程**：未来候选，可大幅降低线程成本；但当前工具链以 JDK 17 为
   目标，且对锁竞争与 IO 拦截行为仍需验证，列为 Phase 7 选项（届时新 ADR）。
4. **Actor 模型（Akka）**：消息隔离好，但框架重量级，调试与序列化复杂度高。

## Consequences

**优点：**

- 支撑 100k 连接与多核扩展；
- 请求路径无全局锁，热点读可接近无锁；
- 背压与异步迁移保证磁盘 IO 不污染事件循环。

**缺点：**

- 并发正确性验证难度高，需要专门的并发测试（JCStress / 并发压力测试）；
- 按 key 分片执行引入调度开销与热点 key 倾斜问题。

**风险：**

- 热点 key 竞争 → 采样感知 + 分片细化/缓存行对齐缓解；
- 死锁/活锁 → 锁顺序规范 + 静态分析 + 压力测试；
- 迁移期间"读旧写新"一致性 → 版本号机制与迁移协议（Phase 6 详细设计）。

## Implementation

- 模块：`network`（Netty）、`command`（分片执行器）、`memory`（分段表）、
  `eviction`/`scheduler`（后台线程）、`metrics`（竞争与队列长度观测）；
- 本 ADR 约束 Phase 1–7 的并发相关实现。
