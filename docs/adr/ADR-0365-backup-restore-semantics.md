# ADR-0365：备份恢复的语义与边界

- 状态：Accepted
- 日期：2026-11-06
- 关联：Phase 10 复核意见 P2、Phase 11

## 背景

备份是**全量逻辑快照**（`SCAN` 导出 JSONL）。之前只实现了"回放"，
但未明确回答四个问题：覆盖还是合并？是否幂等？部分失败怎么办？重复恢复会不会出错？

Phase 10 验收时报告里出现过 `恢复 3006/3008 键` 的表述，实际是两个不同口径混写，
说明语义确实没有写清楚。

## 决策（描述当前实现，并固定为契约）

1. **合并式回放（upsert），不删除备份中不存在的键**
   - 逐条 `DEL key` 后按类型写回（string / hash / list / set / zset），
     因此同键以备份内容为准；
   - 备份**之后**新增、且不在备份中的键**保留**（实测：备份后写入的键恢复后仍存在）。

2. **幂等**
   - 同一份备份重复恢复，结果一致（先删后写，不做追加）。

3. **返回值口径**
   - `POST /backups/{id}/restore` 返回**回放的条目数**（= 备份文件行数）；
   - 与 `record.keyCount`（导出时写入的条目数）来自**同一文件**，二者必须相等，
     已作为不变量写入 E2E 断言。

4. **失败处理：非原子，可能部分恢复**
   - 回放中途出错立即抛出 `502`，已写入的部分**不会回滚**；
   - 失败会写审计 `RESTORE_BACKUP ... result=failed restored=N`。

5. **TPS 与限流**：无内置限速，恢复 3000 级键在本机约 1~2 秒；大批量恢复需自行分批。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 覆盖式（先 `FLUSHDB` 再回放） | 危险且不可逆，控制台不应提供无确认的全量清空 |
| 增量备份（仅导出自上次以来的变更） | 需要变更流与基线管理，当前架构没有，属新功能 |
| 事务化恢复（失败全回滚） | 需要把整份备份写入临时命名空间再切换，成本高 |

## 影响

- 前端与文档统一使用"合并式回放"表述；
- 恢复操作的审计、返回值、失败语义成为可测试契约（E2E-5 已覆盖 4 条断言）；
- 若未来做覆盖式，必须新增显式参数（例如 `mode=replace`）并二次确认，不能改变默认行为。

## 已知限制

- 恢复不做并发保护：两个恢复同时执行会互相覆盖（与备份创建的单实例串行不同）；
- 大备份全量读入内存（`readAllLines`），上限受 `MAX_KEYS` 与堆大小约束。
