# ADR-0370：冷层存活键计数的快照化（G0-5B-1 / F1）

- 状态：Accepted
- 日期：2026-11-07
- 关联：G0-5A（F1）、ADR-0017/0019（冷层与合并）

## 背景

`INFO` 的 `total_keys` 与 `db0` 经由 `TieringReadStorageEngine.size()` 调用
`ColdStorageEngine.liveCount()`。审计发现该方法是"脏标记 + 惰性全量迭代"：
写入之后第一次查询会遍历 pending 与所有 SSTable，逐条过滤 tombstone 与 TTL。
对 10 万级冷键，这意味着一次 INFO 可能触发完整冷层扫描（含磁盘读）。

## 决策

### 1. INFO 只读快照

`liveCount()` 改为返回 `volatile` 快照值，**任何情况下都不在调用线程里扫描**。

### 2. 后台单线程校正

- 写入只做一件事：置脏（原有的 `invalidateLiveCount()`）；
- 后台守护线程 `cold-live-count-refresher` 每 1 秒检查一次，脏则重算并原子发布；
- 单线程 + `synchronized(lock)`：不会重叠执行，也不会与写入并发修改快照；
- 重算抛异常时保留上一次有效快照，下个周期重试。

### 3. 启动时算一次

构造函数在开始服务前同步算一次，避免刚启动时 INFO 报 0。
**这是本方案未消除的残余成本**：冷层越大，启动首帧耗时越长。
持久化计数需要在 manifest 中维护"存活键数"，而 flush/compaction 的键重叠使该值无法
在不做全量合并的前提下精确维护；因此本 ADR 不做持久化计数，如实记录该限制。

### 4. 为什么不做逐键增量

逐键增减看似便宜，但有三类路径无法可靠归属：

| 路径 | 问题 |
| --- | --- |
| `writeTable`（flush / compaction 输出） | 一批条目可能覆盖既有冷键，需逐条回查旧状态，O(批 × 表) |
| compaction | 输入表的存活键与输出表重叠，增量需与更旧的表合并判断 |
| 崩溃恢复 | 内存增量丢失后无法与磁盘状态对齐，仍需全量重算 |

在无法证明"增量与真实状态一致"之前，引入计数器只会制造一个"看起来精确"的假象，
因此选择可验证的快照 + 校正，并把陈旧时间作为明确语义。

## 语义与边界

| 项 | 语义 |
| --- | --- |
| 统计对象 | 逻辑存活键：过滤 tombstone 与已过期条目后的数量 |
| 覆盖写 | 计数不变（合并迭代只取最新版本） |
| 重复删除 | 计数不变（tombstone 覆盖 tombstone） |
| TTL 过期 | 下一次重算后扣减（最长滞后一个刷新周期 + 重算耗时） |
| Flush / compaction | 不改变逻辑键数，重算后一致 |
| 重启 | 构造时重算，结果与磁盘一致 |
| 陈旧上限 | 约 1 秒（刷新周期），重算时长另计 |

## 后果

- INFO 不再随冷层规模变慢；
- `DBSIZE` 同样受益（同一路径）；
- 代价：冷层写入后的一秒内，INFO/DBSIZE 可能比真实值略小；
- 启动仍有一次性扫描成本，已记录为已知限制，不以"优化"名义隐藏。
