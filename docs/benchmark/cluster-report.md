# 分布式集群基准报告（Cluster Benchmark Report）

Phase 11 · 2026-08-10

环境：本机 Windows 11，JDK 21.0.12（编译目标 17），20 核，`-Xmx1g`。

> ⚠️ 口径声明：本基准为**进程内分布式原型**指标——
> Raft 消息走进程内直接调用（无 TCP 网络往返），存储层为各节点独立
> MemTable（无 WAL/SSTable）。因此绝对值不能与真实网络集群直接对比，
> 用于验证：路由开销、复制写延迟量级、复制滞后与选举时间是否符合
> 设计目标（选举 <5s）。

## 单分片吞吐与延迟（3 节点 / 1 shard）

写路径：ClusterClient → slot 路由 → leader → Raft 复制（多数派）→ 本地 apply。

| 指标 | 值 |
| --- | --- |
| 吞吐（20K 复制写） | 154,428 ops/s |
| P50 / P95 / P99 | 0.004 / 0.013 / 0.027 ms |

读路径：ClusterClient → 路由 → leader 本地引擎（无 Raft 往返）。

| 指标 | 值 |
| --- | --- |
| 吞吐（100K 读） | 749,826 ops/s |
| P50 / P95 / P99 | <1 / 1 / 4 μs |

结论：同步复制写（每请求一次多数派往返）量级为几十 μs；读路径
接近纯内存引擎水平。进程内传输下复制写吞吐约 130–155K ops/s，
远低于单机存储层（M ops/s），符合预期——复制是分布式写的主要成本。

## 多分片分布与路由开销（3 shard）

| 指标 | 值 |
| --- | --- |
| 100K 键分布 | shard0=33.2% / shard1=33.2% / shard2=33.3% |
| 原始 slot 计算 | 171 ns/op |
| slot + 拓扑查 leader（完整路由） | 194 ns/op |
| 路由增量开销 | 23 ns/op |
| 路由解析吞吐（100K 键） | 3.03M ops/s |

结论：CRC16/CCITT + 16384 slot 的分布均匀（±0.1%）；完整路由比原始哈希
仅多约 23ns/op，路由不是瓶颈。

## 复制写延迟与复制滞后（3 节点 / 1 shard）

直连 leader 的同步复制写（10K 样本）：

| 指标 | 值 |
| --- | --- |
| 吞吐 | 132,522 ops/s |
| P50 / P95 / P99 | 0.004 / 0.018 / 0.058 ms |

复制滞后（leader 提交后到全部 replica 本地可见，20 样本）：

| P50 | P95 | P99 | Max |
| --- | --- | --- | --- |
| 13–24 ms | 20–35 ms | 20–35 ms | 20–35 ms |

结论：滞后上界 ≈ 35ms（多次运行观测区间 13–35ms），等于 leader 心跳周期
（25ms）内的一次 commitIndex
传播；当前原型在 proposal 中携带的是发送前的 commitIndex，提交后的
新 commitIndex 需下一次心跳下发。真实 Raft 实现可改为提交后立即补发
（预计可降到 sub-ms 量级），已在评审中登记为后续优化点。

## 选举时间（leader 故障转移，5 轮）

| Min | P50 | Max |
| --- | --- | --- |
| 124–142 ms | 196–310 ms | 196–310 ms |

目标：**<5s** ✅（余量 >16×）。

选举流程：leader suspend+close → 剩余节点心跳超时（100–180ms 随机）
→ 发起竞选 → 多数派投票 → 新 leader。

## 结论

- 哈希槽路由：分布均匀、开销可忽略；
- 复制写：P99 ≈ 0.03–0.06ms（进程内），主要成本为同步多数派往返；
- 复制滞后：受心跳周期约束（≤20ms），提交后立即补发可进一步降低；
- 选举：310ms 内完成，满足 <5s 目标；
- 后续：真实 TCP 传输、Raft 日志持久化、多 shard 数据迁移（slot 重指派）。
