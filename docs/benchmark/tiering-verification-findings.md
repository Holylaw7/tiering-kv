# 冷热分层端到端验证：TD-086 发现与修复

- 发现：2026-10-28 · 修复：2026-10-28
- 环境：JDK 21 · 单机（`-Xmx2g`）· 引擎 `memory.limit=128MB`
- 脚本：`scripts/verify-tiering.mjs`（端到端）、`scripts/capacity-probe.mjs`（容量模型）

## 1. 发现的问题：冷层只写不读

修复前实测（60 万确定性键、256B 值）：

| 指标 | 修复前 |
| --- | --- |
| 读回命中 | **311,539 / 600,000 = 51.92%** |
| 丢失 | 288,461 个键返回 nil |
| `DBSIZE` | 311,539（只统计热层） |
| 冷层落盘 | 199.8 MB（两个 SSTable） |
| 读延迟 | P50 0.125 ms（冷热无差异） |

根因：迁移只调用 `cold.put(...)`，而 `src/main` 中**不存在 `cold.get(...)`**；
主读链 `Tracking → HotKey → WAL → MemTable` 从不查询冷层。表现为"超配即丢数据"。

## 2. 修复（TD-086，ADR-0361）

| 层 | 改动 |
| --- | --- |
| 冷层 | 新增 `entry(key)`（暴露 TTL 供回填）与 `liveCount()`（脏标记 + 惰性精确计数） |
| 读装饰器 | 新增 `TieringReadStorageEngine`：`get/exists` 冷层回退、`delete` 双删（写墓碑防复活）、`size` = 热 + 冷、`iterator` 归并去重（热优先） |
| 原子写 | `INCR/APPEND/GETSET/GETDEL/UPDATE` 前 copy-up（先写热层再清冷层，保留 TTL）；`SETNX` 遇冷层键判存在；`TTL/EXPIRE/PERSIST` 感知冷层 |
| 接线 | `Main` 中置于读链最外层；`DBSIZE`/`SCAN`/`FLUSHALL` 随之覆盖冷层 |

## 3. 修复后复测（同一负载）

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 读回命中 | 51.92% | **100.00%（600,000/600,000）** |
| 值不一致 | 0 | 0 |
| `DBSIZE` | 311,539 | **600,000（精确）** |
| 读吞吐 | 24,246 ops/s | **35,246 ops/s** |
| 读延迟 P50 / P95 / P99 | 0.125 / 0.308 / 0.44 ms | **0.100 / 0.183 / 0.299 ms** |
| 早写入段（冷候选）P50/P95 | 0.118 / 0.306 ms | **0.104 / 0.255 ms** |
| 晚写入段（热候选）P50/P95 | 0.139 / 0.320 ms | 0.099 / 0.150 ms |

结论：**冷读只比热读慢约 5%（P50 0.104 vs 0.099 ms，P95 0.255 vs 0.150 ms）**，
因为冷层数据命中 page cache + BlockCache；迁移后数据完整可读。

## 4. 容量模型（TD-084）

方法：清空后分两批写入（键名不重叠），用第二批增量 / 键数得到**边际每键开销**，
剔除首写的一次性段分配开销。

| 值大小 | 每键计量 | 其中固定开销 | 1GB 可容纳键数 |
| --- | --- | --- | --- |
| 100 B | 174.9 B | 74.9 B | **约 614 万** |
| 1 KB | 1,098.4 B | 74.4 B | **约 98 万** |
| 10 KB | 10,313.8 B | 73.8 B | **约 10.4 万** |

拟合：**每键字节 ≈ 值大小 + 74 B**（键 ~20B + 对象头/跳表节点 ~54B）。
容量估算：`可容纳键数 ≈ memory.limit / (valueSize + 74)`。

> 注意：这是**引擎计量**口径，不含 JVM 堆外开销；进程 RSS 另需按
> `docs/benchmark/tiering-vs-redis7.md` 的实测值留出余量。

## 5. 语义变化与已知限制

| 项 | 说明 |
| --- | --- |
| `DBSIZE` | 现在 = 热层 + 冷层存活键数；**精确但惰性**：写入后首次查询触发一次冷层全量扫描（60 万键约 0.2–0.5s），之后命中缓存 |
| `SCAN` | 现覆盖冷层（归并迭代器），大键空间下首次扫描成本上升 |
| `WATCH`/版本号 | 冷层键的 `versionOf` 仍返回热层版本（0），事务守卫对冷层键暂不生效 |
| 读回填 | 冷层读命中**不回填热层**（避免读操作触发写压力）；如需提升冷读命中率可后续加"二次访问回填"策略 |
| `FLUSHALL` | 通过归并迭代器遍历并逐键删除，冷层写墓碑，之后 `liveCount` 归零 |

## 6. 复现

```bash
# 1) 128MB 引擎上限、6380 端口启动
java -Xmx2g -cp target/tiering-kv-5.0.3.jar io.tieringkv.Main   # config: port=6380, memory.limit=134217728
# 2) 写入 60 万键并全量读回
node scripts/verify-tiering.mjs --port 6380 --keys 600000 --value 256
# 3) 容量模型（1GB 上限实例，6381）
node scripts/capacity-probe.mjs --port 6381 --keys 100000 --value 100 --tag b
```
