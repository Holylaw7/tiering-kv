## 二、分阶段详细实测数据

### 2.1 Stage B1 + B2：零分配 RESP 编解码、Netty 批冲刷与分片调度器去争用

核心改造：
- `RespDecoder`（无 `ByteBuf.toString` 零拷贝数字解析、`ByteProcessor.FIND_CR`、无栈单例 `IncompleteInputException`）、`RespEncoder`（静态预编码热响应与整数表 `:0..1024`）、`RespRequestParser`（热 ASCII 命令零分配驻留）；
- `NettyTransportFactory` 引入 `netty-transport-native-epoll:4.1.137.Final`（`linux-x86_64` / `linux-aarch_64`，自动切换 Linux Epoll / 跨平台 NIO 回退）、`PooledByteBufAllocator.DEFAULT`、`FlushConsolidationHandler(256, true)`、`CommandHandler` `channelReadComplete` 批冲刷、`ResponseSequencer` 256 槽环形缓冲；
- `KeyShardExecutor` / `ShardWorker` 消除全局 `AtomicInteger active` 热点（改为每分片 `LongAdder` + 单写 `AtomicLong`、`drainTo(64)` 批量消费、2 的幂位掩码路由）。

**实测回环 TCP 矩阵（`TieringKvServer` + 16 分片 + `TrackingStorageEngine` + `SampledLfuPolicy`，100K 键 × 64B）：**

| 场景 | 吞吐（rps） | P50 延迟 | P99 延迟 |
| :--- | ---: | ---: | ---: |
| `SET c=1 P=1` | `7,330` | `0.136 ms` | `0.281 ms` |
| `GET c=1 P=1` | `12,047` | `0.070 ms` | `0.210 ms` |
| `SET c=50 P=1` | `81,400` | `0.319 ms` | `4.489 ms` |
| `GET c=50 P=1` | `84,795` | `0.297 ms` | `4.548 ms` |

### 2.2 Stage B2：24-bit 内联 Morris-LFU、SkipList 瘦身与 Generational ZGC

核心改造：
- 将 Redis/Valkey 风格 24-bit 热度元数据（16-bit 衰减时间槽 + 8-bit Morris 对数计数器 `[0..255]`，`LFU_INIT_VAL=5`）直接内联进 `KeyValueEntry` 原有对象对齐间隙（**0 字节新增字段开销**），99%+ 热读无需任何 `volatile` 写；
- 新增 `SampledLfuPolicy` 作为默认淘汰策略（`cache.eviction-policy: sampled-lfu`，`tracksViaAccessEvents() == false`），`TrackingStorageEngine` 热路径彻底跳过 `AccessEvent` 分配与锁争用；
- 优化 `SkipList`（`currentMaxLevel` 动态追踪、`remove()` 复用 `updateBuffer`、`numberOfTrailingZeros` 单指令随机层高、O(log N) 抽样），`deploy/Dockerfile` 与 `deploy/console/docker-compose.yml` 默认启用 JDK 21 **Generational ZGC**（`-XX:+UseZGC -XX:+ZGenerational -Dio.netty.allocator.type=pooled`）。

**同机同 JVM 严格 A/B 对照（630,000 键 × 64B，`B4KernelOptimizationBenchmarkTest`）：**

| 策略 | 63 万键存活堆 | 单键真实堆开销 | 8 线程并发 `GET` 吞吐 | 相对对比 |
| :--- | ---: | ---: | ---: | :--- |
| 旧 `LFUPolicy`（全局 `TreeSet` 锁 + 影子索引） | `504.0 MB` | `838.9 B/key` | `472,145 ops/s` | 基线 |
| **新 `SampledLfuPolicy`（24-bit 内联采样）** | **`174.0 MB`** | **`289.6 B/key`** | **`4,310,410 ops/s`** | **堆内存 `-65.5%`，并发读 `9.13×`** |

**`MemoryEngineBenchmarkTest`（Generational ZGC 实测）：**
- 并发写：10 线程 `557,112 ops/s` · 50 线程 `2,770,927 ops/s` · **100 线程 `4,244,590 ops/s`（`0 failures`）**；
- 随机点查：10K 键 `P50 0.6 μs / P99 1.7 μs` · 100K 键 `P50 1.1 μs / P99 2.9 μs` · 1M 键 `P50 3.1 μs / P99 9.4 μs`。

### 2.3 Stage B3：WAL Group Commit、16 分片 S3-FIFO 与零除法冷层加速

核心改造：
- `WALManager` / `WALWriter`：锁外并行编码与 CRC32C 计算 + Leader-Follower Group Commit（上限 `64` 条 / `256 KB`，单次批写 + 单次 `force()` 唤醒整批 Follower）；
- `BlockCache`：升级为自适应 16 分片 SOSP'23 **S3-FIFO**（Small 10% + Main 90% + Ghost 队列，小容量 `<32` 自动单分片保精确容量语义）；
- `ColdStorageEngine`：`ReentrantReadWriteLock` + `ConcurrentHashMap<Long, SSTableReader>` 并发冷读 + 后台无锁 `refreshLiveCount()` + 命中 `BlockCache` 跳过重复 CRC32C；
- `BloomFilter`：无除法 FastRange 映射（`((combined >>> 32) * bitCount) >>> 32`，保持原序列化格式）；`Block.findEntry` 块内原地查找（未命中 0 分配）。

**`B3WalAndColdPerfTest` 实测结果：**

| 测试项 | 实测指标 |
| :--- | :--- |
| WAL Group Commit（`fsync=ALWAYS`，16 线程 × 20 = 320 条） | 合并为 **26 批 `force()`**，**`avgBatch = 12.31` writes/fsync**，总耗时 **`29 ms`**（320/320 崩溃恢复 100% 一致） |
| S3-FIFO 抗扫描污染（120 热块 + 2,000 一次性扫描块） | 热块存活 **`120 / 120`（100%）**，累计驱逐 `1,096` 个扫描块 |
| 冷层 8 线程并发随机点查（与 `refreshLiveCount` 并发） | **`115,349 ops/s`**（G1 默认堆测试下达 `136,822 ops/s`），命中率 **`99.90%`** |
| FastRange BloomFilter（100,000 次探测） | 假阳率 **`0.4150%`**（< 1%），`0` 假阴性，平均 **`165.2 ns/probe`** |

### 2.4 Stage B4：HNSW 零装箱扁平图、SQ8 量化与可插拔 FMA/SIMD 距离核

核心改造：
- `HnswIndex`：邻接表由 `List<List<Integer>>` 重构为扁平原始 `int[][]` + `int[] neighborCounts`；写入预计算单位归一化向量；上层（`layer > 0`）采用零分配 1-NN 贪心下降（HNSW Algorithm 2），层 0 引入 `ThreadLocal<SearchWorkspace>`（代数标记 `visitedGen[]` + 原始类型小/大根堆 `IntFloatMinHeap`/`IntFloatMaxHeap`）；
- `VectorDistanceKernel`：内置 4 路展开 `Math.fma` 的 `ScalarFmaKernel`（零额外 JVM 参数，HotSpot C2 SuperWord 自动向量化），并具备对可选 `jdk.incubator.vector` 模块的运行时安全探测能力与自定义内核注入接口；
- `ScalarQuantizerSq8` + `QuantizationMode (NONE | SQ8 | SQ8_RERANK)`：每向量对称 abs-max int8 量化，支持 `TKHN` v2 持久化格式并 100% 向下兼容 `TKHN` v1 反序列化。

**1) 官方 Phase 65 回归基准（`HnswSearchBenchmarkTest`，20,000 × 64D，`efSearch=48`）：**

## 三、选型与落地建议

1. **生产容器部署**：直接沿用 `v6.3.0` 默认配置即可自动获得 Linux `Epoll` 零拷贝传输、JDK 21 Generational ZGC 低停顿堆管理、`SampledLfuPolicy` 65.5% 存活堆瘦身、WAL Group Commit 与 16 分片 S3-FIFO 抗扫描冷层缓存。
2. **向量检索模式选择**：
   - 内存敏感 / 高维向量（≥ 128D）：推荐 `HnswIndex.QuantizationMode.SQ8`（省 69%~75% 向量内存与 ~50% 磁盘序列化体积，几乎零精度损失）；
   - 极致精度敏感且内存充裕：推荐 `HnswIndex.QuantizationMode.SQ8_RERANK`（可配 `efSearch=64` 达成 97% 召回率）；
   - 兼容历史 `TKHN` v1 下游解析器：保持默认 `QuantizationMode.NONE`（仍全额享受扁平邻接数组、`ThreadLocal` 零装箱搜索与 FMA 核带来的 `2.6× ~ 3.5×` 延迟下降）。
