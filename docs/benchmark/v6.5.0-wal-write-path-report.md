## 一、优化动机与根因定位

在 `v6.4.0` 全栈容器压测中，数据面纯内存读路径（`GET c=50, P=16`）已达 `643k–651k rps`，但同口径高管线写路径（`SET c=50, P=16`）在 `WAL EVERY_SEC`（`90.5k rps`）与 `WAL NO`（`92.0k rps`）下表现几乎相同，甚至低于 `v5.0.0` 基线（`161.3k rps`）。结合源码与提交历史精确定位了五层叠加瓶颈：

1. **B3 无自旋 `parkNanos` 引发 `futex` 唤醒风暴**：对 `EVERY_SEC`/`NO` 同样走全局 `commitQueue`，Follower CAS 失败后零自旋直接 `LockSupport.parkNanos(1_000_000L)`；
2. **16 分片汇聚单 WAL 写锁**：全部 `ShardWorker` 共享单 `recordSequence`、单 `writeLock` 与单段文件；
3. **管线并发坍缩**：`ShardWorker` 批拉取 64 条任务后逐条同步写 WAL，800 在途请求在 WAL 层被压缩为 ≤16；
4. **高频堆分配 + 多层缓冲拷贝 + 无向量读冗余**：每条 `SET` 分配 `WALEntry`/`byte[]`/`ByteBuffer`/`CRC32C`/`CommitTicket` 并在无向量场景下经 `VectorIndexSyncStorageEngine` 触发一次完整全栈 `delegate.get(key)`；
5. **元数据刷盘与微批次 syscall 放大**：未预分配段文件且调用 `force(true)`。

## 二、三阶段纯 Java 21 架构落地

- **Phase 1（Sharded WAL + 64 KB 堆外聚合缓冲 + `Checkpoint v2` 无锁低水位）**：
  - `WalShardRouter` 采用与 `ShardRouter` 同源 FNV-1a 32-bit 路由将 WAL 拆为 16 路独立 `WALShard`（与 256 桶 `ReentrantLock` 条带严格互斥不相交）；
  - 每分片独享 64 KB 堆外 `stageBuffer`（`NO`/`EVERY_SEC` 下零堆分配直编，满 64 KB 或 500 ms 定时刷盘，系统调用缩减约 200×；`ALWAYS` 下采用自适应 64 次自旋 + 50 µs 短退避 Group Commit）；
  - `CheckpointManager` 升级 `VERSION=2`（分片位点向量 + 整文件尾部 CRC32C，兼容 v1 读取），各分片通过 `InFlightApplyTracker` 暴露无 STW 安全低水位；`ShardedRecoveryManager` 支持旧版单 WAL 自动无损升级、16 线程并行恢复与变更 `wal.shards` 归并重分片。
- **Phase 2（`ShardWorker` 连续写批聚合 + 全存储装饰链透传）**：
  - 引入 `BatchableShardTask` 与 `WriteOp`，`ShardWorker` 对 `drainTo(64)` 中的连续 `SET`/`DEL` 合并为单次 `StorageEngine.applyWriteBatch`（零 `ArrayList` 堆分配，遇任何读命令或读改写命令立即切断刷出，100% 保持同键 Read-Your-Own-Writes 线性一致；OOM 下拒 `SET` 放行 `DEL`）；
  - `VectorIndexSyncStorageEngine` 在 `vectorStore.size() == 0` 时跳过无意义前置 `delegate.get(key)`。
- **Phase 3（4 MB 分块预分配 + `fdatasync` + 纯 Java 21 `O_DIRECT` + 可观测性）**：
  - `LogSegment` 落地 4 MB 分块预分配（16 分片冷启动仅预分配 64 MB，耗时 < 150 ms）与 `channel.force(false)`（`fdatasync`），`WALReader` 识别预分配全零尾区为干净逻辑 EOF；
  - 支持基于 JDK 21 `ExtendedOpenOption.DIRECT` + `ByteBuffer.alignedSlice(blockSize)` 的 4 KB 对齐尾页覆写（`wal.io-mode: direct`，不支持挂载自动探测回退 NIO）；
  - `deploy/console/docker-compose.yml` 拆出独立 `core-wal:/app/data/wal` 挂载卷，`INFO persistence` 与 `/metrics` 暴露 `tieringkv_wal_*` 实时后端、分片数、批均大小与 `fsync` 耗时指标。
