# 项目缺口审计（论文之后的工程收尾）

审计日期：2026-11-06　基线：`087c24e`　方式：代码走查 + 配置检查 + 已知测试结果

## 结论先行

代码里**没有遗留的 TODO/FIXME 桩**（`src` 中 3 处匹配均为测试断言"文档不得含 TODO"），
`UnsupportedOperationException` 均为设计上的显式失败（原子操作、timeoutNow），不是未完成实现。
真正的缺口集中在**运维语义**与**验证边界**两类，共 6 项值得处理。

## P0：一致性与数据安全

### 1. 恢复操作没有并发保护，也没有"进行中"状态

- 证据：`BackupService.restore()`（第 205 行）直接从备份记录读文件并逐条回放，**没有任何锁**；
  对比 `export()` 第 103 行有 `synchronized (lock)` 的按实例串行化。
- 后果：同一实例并发发起两次恢复，两条回放流交错执行，最终数据取决于调度顺序；
  页面与审计只能看到两次"成功"。
- 这与此前修复的 TD-101（并发备份）是**同一类缺陷的另一个入口**。

### 2. 恢复非原子，失败后无"部分恢复"标记

- 证据：`restoreEntry()` 对每个键执行 `DEL` + 写入，异常时只记审计并抛出，已写入的键保留；
  备份记录状态不变（`BackupStatus` 只有 RUNNING/SUCCESS/FAILED，且恢复不产生记录）。
- 论文已如实声明"合并式恢复、非原子"，但产品上缺少提示：用户无法区分"恢复了一部分"和"完全没恢复"。

### 3. 备份文件没有保留/清理策略

- 证据：`BackupService` 只有手工 `delete(recordId)`；全仓库无 retention/TTL 定时任务。
- 后果：长期运行后备份目录持续增长，直至磁盘写满；写满后失败点出现在导出中途。

## P1：安全与部署

### 4. JWT 密钥带开发默认值，生产可能直接沿用

- 证据：`application.yml` 中 `jwt.secret: ${CONSOLE_JWT_SECRET:tiering-kv-console-dev-secret-key-...}`。
- 风险：部署时忘记设置环境变量，系统仍能启动，但令牌可被离线伪造。
- 建议：`prod` profile 下取消默认值（缺失即启动失败），并加一条启动自检。

### 5. 备份目录无磁盘水位检查

- 证据：导出写文件前不检查剩余空间；只在写入异常时失败。
- 建议：导出前检查可用空间 ≥ 预估大小（或固定阈值），不足直接返回明确错误码。

### 6. `/actuator/info` 匿名可读

- 证据：`SecurityConfig` 第 53 行放行 `/actuator/health`、`/actuator/info`。
- health 放行是惯例；info 若包含构建/版本信息，建议改为认证后可见或直接关闭。
