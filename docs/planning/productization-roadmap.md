# 产品化路线图（依既有文档方案）

基线：`8823068`　依据：RFC-0002、Product Completeness Baseline v2、Quality Gates、GA Operations Closure、v4.0 Roadmap

## 0. 先对齐"产品级"这个词在本项目里的定义

仓库现有文档已经把能力分成三档（`product-completeness-baseline-v2.md`）：

| 档位 | 含义 | 当前归属 |
| --- | --- | --- |
| **PRODUCT** | 有语义承诺、错误码、压测基线与真实环境证据 | RESP/命令面、存储、Raft、事务、数据结构、消费组基础 |
| **EXPERIMENTAL** | 功能可用但未做转正评审与门禁升级 | SQL、向量、SaaS、AI |
| **ADAPTER** | 只有接口与降级路径，数据面为模拟 | 量子授时、S3、Spot |

所以"向产品级迈进"在本项目里不是一句口号，而是三件事：

1. **把已声称 PRODUCT 的能力补上生产语义**（并发、保留、密钥、磁盘水位）；
2. **把 EXPERIMENTAL / ADAPTER 按 RFC-0002 转正**（真实动作执行器、真实对象存储、转正评审）；
3. **让每条承诺都有可复现的环境证据**（真实 Runner、真实 K8s、真实对象存储）。

## 1. 差距总览（对照 RFC-0002 的四个工作包）

| 工作包 | RFC 范围 | 当前状态 | 本次审计新增缺口 |
| --- | --- | --- | --- |
| WP-A K8s Operator 生产化 | 真实动作执行器、CRD/RBAC、kind CI | `ActionApplier` 仅有日志实现；镜像停在 v3.7.0 | — |
| WP-B 真实对象存储 | S3/MinIO 数据面、备份接线、故障注入 | `S3ObjectStorage` 是内存 map | — |
| WP-C 能力转正 | SQL/向量/SaaS 转 PRODUCT | 未做转正评审 | — |
| WP-D 发布收尾 | 门禁 3 连绿、Trivy、镜像、Release notes | v4.1.0 已 GA | — |
| **WP-0（本文新增）** | 单机生产语义 | 未覆盖 | **恢复并发无保护、恢复非原子、备份无保留、JWT 默认密钥、无磁盘水位、/actuator/info 匿名** |

> WP-0 是从"能演示"到"敢上线"之间最便宜的一段，RFC-0002 没有单列，但它挡在 WP-A 之前：
> Operator 做得再好，恢复并发仍会互相覆盖，产品承诺就不成立。

## 2. 五个阶段

### G0　单机生产就绪（约 5–8 人日）

目标：**单机部署可以被当作生产实例使用**，不含高可用承诺。

| 任务 | 现状 | 验收 |
| --- | --- | --- |
| G0-1 恢复互斥 + `RESTORING` 状态 | `restore()` 无锁 | 并发恢复 200/409；失败标记"部分恢复 restored=N" |
| G0-2 备份保留策略 | 仅手工删除 | 造 5 份备份，按保留策略清理后剩 N 份 |
| G0-3 生产密钥强制 | JWT 有开发默认值 | 不设 `CONSOLE_JWT_SECRET` 启动失败 |
| G0-4 备份目录水位检查 | 无 | 可用空间不足时返回明确错误码 |
| G0-5 `/actuator/info` 收敛 | 匿名可读 | info 需认证或关闭 |
| G0-6 SLO 与告警接线 | `slo-sla.md` 有定义 | 三个 SLO 有对应指标与告警规则 |
| G0-7 演练一次 | `upgrade-backup-drills.md` | 按 runbook 完成备份→恢复→升级演练并留记录 |

交付物：G0 评审记录、演练报告、更新后的 `operations-runbook.md`。

### G1　云原生交付（RFC-0002 WP-A，约 13–19 人日）

关键是把**日志动作**换成**真实动作**：

- `K8sActionApplier`：OperatorAction → StatefulSet/Deployment/Service/CronJob 的真实变更，带 ownerReference 与 finalizer；
- CRD 完善：status subresource、validation、RBAC、LeaderElection；
- 生命周期演练：创建→就绪→扩容→镜像升级→备份 CronJob→删除清理，含失败注入；
- `k8s-e2e.yml`：kind 集群 → 装 CRD → 部署 Operator → apply CR → 断言 status → RESP 冒烟 → cleanup。

验收：真实 Runner 的 `k8s-e2e` 全绿，一条 CR 走完全流程；ADR-0353 记录决策。

### G2　真实外部依赖（WP-B，约 13–18 人日）

- MinIO/S3 真实数据面：Put/Get/Delete/List + multipart + 超时重试限速；
- 备份/恢复接真实对象存储：大对象、断点、校验、生命周期清理；
- MinIO 容器 CI：权限策略、100MB+ 大对象、连接中断与限速注入；
- Spot/市场 API 从 fake 换真实 HTTP（限流/缓存/降级）。

验收：MinIO 上完成一次全量备份 + 恢复 + 大对象用例；ADAPTER 升级为"真实 + 降级"双路径。

### G3　能力转正（WP-C，约 17–25 人日）

转正不是"改个标签"，而是先立标准再评审：

| 步骤 | 内容 |
| --- | --- |
| C1 转正标准 | promotion checklist：语义、错误码、边界、兼容承诺、SLA、压测基线、真实环境证据 |
| C2 SQL 转正 | 2PC 接线、错误码与 EXPLAIN 完整性、并发/容量边界、压测基线 |
| C3 向量转正 | HNSW 并发读写、持久化恢复、容量模型、冷热口径补测 |
| C4 SaaS 转正 | 租户隔离、配额、计量计费、审计导出、多租户权限 E2E |
| C5 门禁升级 | release workflow 纳入转正能力门禁；README/白皮书能力分层同步 |

### G4　发布与承诺（WP-D，约 3–5 人日）

全量回归 + 门禁 3 连绿 + Trivy 0 漏洞 + GHCR 镜像 + Release notes；
`CHANGELOG`/`ROADMAP`/`README`/能力分层基线同步；SLO 报告归档。

## 3. 关键路径与依赖

```text
G0 单机语义 ──► G1 Operator ──► G2 真实对象存储 ──► G3 转正 ──► G4 发布
      │                │
      └─ SLO/演练 ─────┘（G1 的失败注入复用 G0 的演练脚本）
```

- **G0 必须先行**：G1/G2 的故障注入与演练都依赖"恢复语义正确"这一前提；
- **G1 与 G2 可并行**：一个面向编排，一个面向存储，改动面不重叠；
- **G3 依赖 G1+G2**：转正要求"真实环境证据"，没有 Operator 与对象存储就无法给 SQL/向量/SaaS 出证据。

## 4. 工作量与排期（沿用 RFC-0002 口径）

| 方案 | 范围 | 人日 | 单人 | 双人 |
| --- | --- | --- | --- | --- |
| 最小补证 | G0 + WP-A 的 A4（kind CI） | 8–12 | 2–3 周 | 1–2 周 |
| 推荐 | G0 + G1 + G2 最小闭环 | 31–45 | 6–9 周 | 3–5 周 |
| 完整 | G0–G4 全量 | 51–75 | 2.5–4 人月 | 6–8 周 |

> 与 RFC-0002 的 46–67 人日相比，完整方案多出 5–8 人日，即 G0 部分；其余口径一致。

## 5. 不能靠"改代码"解决的三件事

| 事项 | 为什么 | 处理方式 |
| --- | --- | --- |
| 跨机共识证据 | 需要多台物理机/网络可控环境 | 用 kind + 网络策略模拟只能算"编排层证据"，不能替代真实跨机；对外表述必须收窄 |
| 掉电安全 | 需断电/块设备损坏注入 | 依靠 `RealBlockDeviceChaosTest` 一类测试在 Linux 真机补证；当前 13 项跳过里有 6 项属此类 |
| 生产 SLA 承诺 | 需要长期运行与容量数据 | 先给 SLO 目标与测量方法，历史数据积累满一个周期后再谈 SLA |

## 6. 建议的第一步

如果只做一件事，做 **G0-1（恢复互斥 + RESTORING 状态）**：

- 它是审计里唯一的 P0 正确性问题；
- 改动小（复用 export 的按实例锁 + 一个状态字段），一次提交可完成并配单测；
- 它同时补上了论文 TD-101 案例"同类缺陷另一入口"的漏洞，对答辩是加分项。

做完 G0-1 再决定是否继续 G0 其余五项——那五项更偏运维完备性，可以批量做。
