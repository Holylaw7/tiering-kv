## 核心变更

### 1. Operator 核心修复与声明式全生命周期协调（A1）
- **入口与 CRD 契约对齐**：修正 `tiering-operator/pom.xml` 主类为 `io.tieringkv.operator.k8s.TieringKVOperator`，补齐 `K8sTieringKVCluster` 的 `@Kind("TieringKVCluster")` 与 `Namespaced` 标记接口；`deploy/operator/tieringkvcluster-crd.yaml` 声明 `subresources.status: {}`、`additionalPrinterColumns`（`Phase / Meta / Storage / Gateway / Image / Age`）、可选规格字段（`gatewayReplicas`、`storageClassName`、`metadataStorageSize`、`storageDataSize`）与完整状态字段（`phase`、`lastBackupJob`、`lastBackupStatus`、`lastBackupTime`、`message`）。
- **不可变字段安全 Patch 与真实探针**：修正存储层 Pod 启动角色为 `ROLE=participant`（`start.sh` 兼容 `participant|storage`）；`StatefulSet` 与 `Service` 在扩容、滚动升级及重复协调时使用安全 `edit()` Patch，不触碰不可变 `volumeClaimTemplates` 与已分配 `clusterIP`；三层工作负载统一挂载 TCP `readinessProbe` / `livenessProbe` 与 `tieringkv.io/config-hash` 配置哈希注解。
- **真实 RESP 备份与最小权限清理**：备份 `CronJob` 默认启用（`suspend: false`）并执行真实 RESP 探活与快照命令（`PING` / `DBSIZE` / `BGSAVE`）；支持通过 CR 注解 `tieringkv.io/backup-request-id` 按需拉起一次性 `batch/v1 Job` 并回写 `lastBackupJob` / `lastBackupStatus` / `lastBackupTime`；`deleteCluster()` 按名称逐一以 `DeletionPropagation.BACKGROUND` 清理备份 Job（无需 `deletecollection` 权限），并严格保留全部 PVC 不销毁持久化数据。

### 2. Operator 生产运行态加固（A2）
- **健康探针与高可用选主**：新增零外部依赖 JDK `OperatorHealthServer`（`:8088`，`/healthz` 存活与 `/readyz` 动态就绪）与基于 `coordination.k8s.io/v1 Lease` 的 `OperatorLeaderElector`（抢占、续租、过期接管与停机主动释放）。
- **并发与权限安全**：`TieringKVOperator` 引入每 CR 细粒度 `ReentrantLock` 互斥、`WATCH_NAMESPACE` 隔离与 `SIGTERM` 优雅停机；`Fabric8OperatorClient` 显式命名空间绑定、已有资源走 `replace()`、`resourceVersion` 同步与状态回写 `409` 自动重拉重试。
- **生产部署清单**：新增最小权限 `deploy/operator/rbac.yaml`（`persistentvolumeclaims` 仅 `get/list/watch`，禁止删除）、非 root（UID `10001:10001`）`deploy/operator/deployment.yaml` 与 `deploy/operator/kind-cluster-sample.yaml`，补齐 `deploy/Dockerfile.operator` 容器级健康检查。

### 3. 真实 `kind` 集群 6 阶段 E2E 门禁与 4 镜像发布（A3）
- `K8sActionApplier.ready(...)` 感知滚动升级过程中的 `updatedReplicas`，防止旧副本就绪数提前触发 `READY` 误判。
- 新增 `scripts/kind-operator-e2e.sh` 并在 `.github/workflows/transaction-e2e.yml` 新增 `operator-kind-e2e` 真实 Kubernetes 门禁，完整实测 6 大阶段：
  1. 部署 CRD / RBAC / Operator，校验 `/healthz` + `/readyz` 及 Lease `tiering-kv-operator-leader` 选主成功；
  2. 创建 CR `demo`（`1/2/1`）达到 `phase=READY` 并完成 RESP `SET/GET` 冒烟校验；
  3. 在线扩容 `storageReplicas 2 → 3`（验证安全 Patch 无 `422`）并断言 `regions.conf` 自动补全 `demo-storage-2 r3`；
  4. 滚动升级 `e2e-v1 → e2e-v2`，全三层工作负载切换完成重回 `READY` 且 RESP 读写正常；
  5. 注解触发按需备份 Job `demo-backup-e2e-1`，断言 `SUCCEEDED` 与 CR 状态回写一致；
  6. 删除 CR 触发 Finalizer，断言自有工作负载/Job/ConfigMap/Service 全部清理且 4 块 PVC 完整保留。
- 发布流水线 `.github/workflows/release.yml` 升级至 4 镜像 GHCR 发布并自动附带 `checksums.sha256` Release 资产。
